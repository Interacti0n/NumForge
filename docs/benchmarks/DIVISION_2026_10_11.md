# Limb division — 11 October 2026

Follow-up to [factor grouping](FACTORIAL_GROUPING_2026_10_11.md) and
[the cross-layer audit](PERFORMANCE_AUDIT_2026_10_10.md). The public C API,
numeric semantics and production time/allocation/output limits are unchanged.

## Implementation

The previous magnitude division shifted the remainder and compared/subtracted
the divisor once for every input bit. It is replaced with:

- direct zero/smaller/equal operand handling;
- one 128-by-64-bit step per input limb for a single-limb divisor;
- normalized long division in radix 2^64 for larger divisors, including
  quotient-estimate correction, remainder-overflow handling and add-back;
- temporary normalized buffers, checked size arithmetic and budget checkpoints
  for each quotient digit and every 256 limbs in longer inner loops.

The public wrapper no longer duplicates both inputs: the kernel reads them and
writes fresh outputs, and all reads/sign inspection finish before either output
is committed. Failed allocations or cancellation preserve both destinations.
Negative division still truncates toward zero; remainder has the dividend's sign.

Native 128-bit arithmetic or the MSVC x64 intrinsic remains an implementation
choice for the scalar helper. Platforms without either retain its portable
64-step helper. `NUMFORGE_TEST_PORTABLE_DIVISION` can force that helper in a
test-enabled build; using it outside allocation-test builds is rejected.

## Direct measurements

Same Windows PC, MSVC Release. A fresh before-change recording starts from
`51efef6`. Final after-change measurements run serially after all other tests
and builds finish. BigInt values are seven-sample medians, with separate
warm-ups and allocation probes. Complete exact references are checked outside
timing. No wall-clock threshold is added to CI.

| Fixture | Before | After | Approximate speedup |
| --- | --- | --- | --- |
| 4096-bit dividend / 97 | 89.11 µs | 0.724 µs | 123x |
| Similar 4096-bit operands | 188.11 µs | 1.008 µs | 187x |
| 4096-bit / 2048-bit | 410.10 µs | 6.215 µs | 66x |
| Exact 6144-bit / 2048-bit | 730.53 µs | 10.193 µs | 72x |
| GCD of consecutive Fibonacci numbers, about 1423 bits | 29.60 ms | 1.119 ms | 26x |

Allocation calls fall from 4 to 2 for the single-limb fixture and from 10 to 4
for the three general-division fixtures. The Fibonacci GCD probe falls from
15,589 calls / 1,350,152 requested bytes to 8,010 calls / 684,848 bytes.

Public C API `log10(2)` at 2000 significant digits takes **1.089–1.125 s** in
three independent single-call processes, versus a fresh **9.166 s** before-change
measurement (the earlier audit measured 8.795–8.979 s). Its full reference is exact.

## Complete calculator pipeline

The calculator uses output places plus working guard precision, so these calls
are not identical to the C API precision benchmark. Auto, 2000 places, 5000 ms;
three fresh processes per row. Before values here are the earlier audit.

| Expression | Audit result | After division change |
| --- | --- | --- |
| `ln(2)` | Success, 4.484–4.609 s | Success, 0.575–0.592 s |
| `sin(1E100)` | Time limit, 3/3 | Success, 0.573–0.588 s |
| `tan(1+i)` | Time limit, 3/3 | Cumulative allocation limit, 0.768–0.807 s |
| `ln(2)+ln(3)` | Time limit, 3/3 | Cumulative allocation limit, 0.885–0.898 s |

The valid calculator spelling `log(2;10)` also reaches the cumulative allocation
limit in 0.865–0.890 s. An initial exploratory `log10(2)` calculator probe was a
syntax error because that C API name is not calculator syntax; it is excluded
from performance conclusions. Production failure rows are not successful results.

A complete `100000!` regression still returns `2.824229408E+456573` with the
normal 5-second deadline, in 1.763 s (one sample). Its factorial algorithm is
unchanged by this division work.

## What remains expensive

A separate unbudgeted C API log10 allocation probe requests **83,342,069 bytes**
across **177,304 allocation calls**, while peak tracked live payload is only
**21,664 bytes**. The audit had 92,015,325 requested bytes / 199,663 calls and
27,840 peak live bytes. Requested volume is not physical memory use: free()
does not reset the calculator's cumulative 64 MiB budget.

The separate phase diagnostic reports about 437 ms in the integer core and
670 ms in aggregate other decimal work, versus about 8.108 s / 0.660 s in the
audit. Instrumentation has its own overhead and these are separate calls, not
subdivisions of the headline samples. The next candidate is reducing repeated
temporary-object and scratch-buffer allocation in high-precision math, with
local ownership and failure guarantees retained. Raising the budget alone
does not address that churn. Integer-core phase totals do not isolate division.

## Verification

- 13,848 independent native JavaScript BigInt quotient/remainder checks per
  backend: all 64 normalization shifts, exact/near-exact results, zero quotient
  digits, maximal digits, correction/add-back constructions, four sign pairs,
  all seven distinct-input output-alias configurations and near-protocol-cap
  operands. `division_oracle_tests` is a regular CTest when Node is available.
- Existing numeric oracle: 8,395 cases pass per backend; the existing 16 allowed
  directed-rounding cases retain their one-ULP contract.
- Both oracles and integer/allocation suites pass on MSVC x64, GCC x64,
  GCC forced-portable helper and actual MSVC Win32.
- Expanded failure tests exhaust allocation positions and deterministic budget
  checkpoints in short, single-limb, normalized, estimate-correction and
  add-back cases, for every distinct-input alias configuration. Failed outputs
  and all inputs remain unchanged. Identical input pointers are tested too.
- Twelve rebuilt dependent MSVC suites pass: integer/decimal properties,
  rational/complex numeric, calculator/contract/complex, session/application,
  unit web and HTTP API.
- The complete 1,067-row decimal/math reference corpus passes: 1,058 expected
  successful rows and nine expected domain/scale failures; 16 legacy directed
  results use their existing bounded rule. This full run is functional
  verification, not a fresh-process latency comparison.

Raw local CSV, full reference validation and profiling output are in ignored
`build/performance-division-2026-10-11`. An initial attempt to force portability
by undefining the compiler's native-width macro conflicted with MinGW headers;
the final test-only helper switch avoids changing system macros. No server
restart, push or release is included.
