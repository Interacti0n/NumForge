# Backup and recovery qualification on 5 November 2026

## Daily backup format 2

`scripts/ops_backup.py run` now includes a consistent standalone Kuma database
alongside the PostgreSQL logical dump, committed Git bundle and allowlisted private
configuration. SQLite `VACUUM INTO` runs through the actual installed Node binding,
includes committed WAL data and uses a random temporary filename. Binary streaming
avoids Docker archive-copy limitations with the container's `/tmp` tmpfs.
The temporary container file is removed on success and failure.

Both database files are staged under the existing private `.local/ops` directory.
The exact Restic snapshot is restored; every staged file is SHA-256 compared,
PostgreSQL is restored into a disposable database and SQLite is opened read-only
for `integrity_check` and required Kuma tables. Only then may the existing policy
retain 7 daily, 4 weekly and 6 monthly `numforge-pilot` snapshots and report success.
The existing Windows daily task already calls this script, so no second task was
registered. Its next automatic execution remains a separate operational check.

The first successful format-2 snapshot is
`25676eec9b107914ecd11dd88c053a7c43c389fa2f3947702850314ec7c65229`,
completed at `2026-11-05T22:29:13Z`, from source commit `4697a47`.
The monitor snapshot contains one user, six monitors and 14,512 heartbeats.
Private status and logs are in `.local/ops/backup-status.json` and `backup.log`.
Snapshots taken before this change do not acquire monitor coverage retroactively.

The scope excludes Docker images, the gateway's private CA volume, monitor
attachments, uncommitted source and the Restic recovery password. The databases
are independently consistent, not a cross-service atomic transaction. The password
must be available separately from both the PC and backup disk.

## Isolated restored-stack rehearsal

```sh
python tests/containers/check_recovery.py --daily --output build/recovery-UNIQUE
```

This restores the verified daily snapshot from Restic, creates a randomly named
Compose project with fresh volumes and an internal network, provisions database
roles, restores PostgreSQL and Kuma, then starts the five services from immutable
local image IDs. It publishes no ports, runs no tunnel, and copies no live CA key.
A new disposable CA is generated for the fixture. File bind mounts are rebound to
fixture copies. The image build contexts and original network/volume names are removed.
The one-shot monitor copy helper alone gets CHOWN/DAC_OVERRIDE to populate a fresh
volume; normal services retain their original restrictions.

The successful run is recorded in
`build/followup-20261105/daily-recovery-3/result.json`: five healthy services,
11 restored account tables, native Node SQLite integrity and gateway HTTPS checks,
and no remaining fixture containers, networks or volumes. Two earlier attempts
exposed copy-helper ownership/capability requirements; both removed their resources.
Unit tests cover resource rebinding, forbidden project names and corrupt manifests.

**Limit:** this uses the existing Docker engine, locally available images and two
local bind files. It does not prove recovery on a clean Windows host, preserving
the original CA, a user's browser login after recovery or externally reachable
monitor probes. External connectivity is deliberately disabled in the fixture.

## Prepared encrypted recovery kit

```sh
python scripts/ops_recovery.py capture
python scripts/ops_recovery.py verify --directory RESTORED_KIT_DIRECTORY
python tests/containers/check_recovery.py --kit RESTORED_KIT_DIRECTORY --output build/kit-recovery-UNIQUE
```

The capture command first makes a verified daily backup, then prepares a separate
`numforge-recovery-kit` Restic snapshot containing:

- that daily data/configuration/Git bundle;
- a Docker archive of the exact five healthy deployed image IDs;
- copies of the runtime file bind mounts, including the Caddyfile and monitor setup helper;
- the gateway PKI tree, including the **private CA key**;
- a manifest with image IDs, bind mappings and SHA-256 for every payload file.

The exact kit is restored and all bytes checked before success is recorded.
The kit has no automatic pruning policy yet. Temporary plaintext kit/restore
directories are removed at exit; the existing daily staging directory remains private.
PKI is copied online, so a future CA rotation requires a controlled consistency
check. A saved public root certificate alone cannot replace the private CA key.

**Current status:** automatic approval review rejected execution because prior
backup authorization did not cover exporting the private CA key. Explicit consent
was requested; the full capture and `--kit` rehearsal have not run. This branch is
prepared and unit tested, not qualified as a completed portable recovery solution.
The daily-only rehearsal above completed independently without accessing that key.
